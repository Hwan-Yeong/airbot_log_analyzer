# 로봇 로그 분석 지침 (공개용 예시)

> 실제 현장 분석에서 쌓은 원칙을 일반화한 예시입니다. 하드웨어 사양(비트 정의·임계값·주소·포트), 코드 위치,
> 개별 시료 사례 기록은 포함하지 않습니다. 회사 내부 버전은 같은 구조에 사양과 사례가 추가됩니다.

## 1. 분석 원칙
- **사실과 추정을 분리**해서 적는다. 결론은 "확인된 사실 / 미확인 / 추가 확인 필요"로 나누고, 원인 후보는 근거와 함께 "단정 불가"로 남긴다.
- **틀린 추정은 정정 기록**을 남긴다 (예: "A 가 안 붙음"이 아니라 "A 는 붙어 송신했고 B 가 응답 못 함").
- **접수 증상 ≠ 로그상 현상**일 수 있다. 재현되지 않으면 그렇게 적는다. 메일의 날짜·시각이 틀린 경우도 있다.
- **계층을 나눠 본다**: 물리 링크 → IP → 앱 세션 → 앱 → OS. 한 계층이 정상이라고 다른 계층을 정상으로 추론하지 않는다.
- **로그가 없다는 것은 정상도 이상도 아니다.** 그 로그가 원래 언제 기록되는지(주기/변화 시에만/특수 모드에서만)를 먼저 확인한다.
- **두 시스템(주행부 AMR, 화면부 SoC) 로그를 교차 검증**한다. 한쪽 로그만으로 결론 내리지 않는다.

## 2. 로그 구성과 시각
| 로그 | 형식 | 주의 |
|---|---|---|
| AMR 앱 로그 `airbot_log*.txt` | `[YYYY-MM-DD hh:mm:ss.mmm] [노드] [레벨] 메시지` | 회전(.1~.9, 숫자가 클수록 오래됨). 멀티라인 덤프는 앞 줄의 시각을 따름 |
| AMR 서비스 로그 `otalog*.log` | `[YYYY-MM-DD hh:mm:ss] [레벨] 메시지` | 초 단위. 네트워크 감시 줄은 **상태가 바뀔 때만** 기록 |
| AMR journal / dmesg 스냅샷 | journal: `Mon DD hh:mm:ss host 프로세스: 메시지` / dmesg: 부팅 후 경과초 | 연도 없음. 링크 이상 순간에 저장된 스냅샷이라 연속 로그가 아님 |
| SoC logcat (`logcat`, `logcat.N.gz`) | `MM-DD hh:mm:ss.mmm PID TID 레벨 태그: 메시지` | 연도 없음, 숫자가 클수록 오래됨, 한 파일이 여러 날짜에 걸침 |

- **부팅 직후 시계**: 시각 동기화 전에는 기본값(과거 고정 시각)으로 찍히다가 실제 시각으로 점프한다. 매 부팅마다 같은 과거 시각에서 시작하면 RTC 정지를 의심한다.
- **한 파일 안에서 시각이 비단조**일 수 있다 → 시간순 정렬이 아니라 **부팅 세션 단위**로 끊어 본다. 같은 시각이 반복 삽입되는 줄은 버퍼링된 로거의 늦은 출력(잡음)일 수 있다.
- **두 시스템의 시계 차이는 시료마다 다르다**(수 초~수십 초). 같은 사건을 양쪽에서 찾은 기준점(시각 동기화 명령의 페이로드, 송신↔수신 쌍)으로 차이를 구하고, 타임라인은 AMR 시각 기준으로 통일한다. 원래 시각은 원문에 남긴다.
- 클라우드 상태 보고의 `...Z` 시각은 UTC, 화면 표시 시각은 현지 시각일 수 있다.

## 3. 기록 정책 — "없는 로그"를 해석하는 법
- 주기적으로 보내는 값(예: 1초 주기 상태 송신)은 부담 때문에 **로깅하지 않는** 경우가 있다 → AMR 로그만으로 "송신 값이 멈췄다"를 판단할 수 없다. 수신 측(SoC) 로그로 교차 확인한다.
- 특수 모드(자가진단 등)에서만 나오는 메시지의 공백은 "데이터 멈춤"이 아니라 "모드 미동작"이다.
- 경고·오류성 감시 로그는 **임계를 넘을 때만** 기록된다 → 0건은 "임계 미만"일 뿐이다.
- 상태 변화 시에만 기록되는 감시 로그가 장기간 없으면 그 기간이 **안정적이었다는 방증**이 될 수 있다.

## 4. 재부팅·재시작 판별
| 판별 | 전원 순단(콜드) | 정상 재시작(앱/OS) | 앱 무응답(재시작 없음) |
|---|---|---|---|
| 재시작 직후 시각 | 기본값/정지된 RTC 값으로 돌아감 | 직전 시각에서 연속 | - |
| 서비스 종료 기록 (`Received signal: SIGTERM`) | 없음 | 있음 | 없음 |
| 직전 줄 | 문장 도중 끊김 + NUL 패딩 | 정상 종료 | 로깅만 멈춤 |
| SoC 동반 재부팅 | 거의 동시에 동반 | 없음 | 없음 |

- 앱 기동 마커(`heartbeat_check ... Expected software version`)는 OS 부팅과 앱 재시작 양쪽에서 나온다 → 이것만으로 재부팅이라 하지 않는다.
- SoC 가 보낸 시각 동기화 명령(`soc-cmd received : reqSetTimeData ...`) 수신 = **재부팅 후 SoC 재연결 기준점**.
- SoC `bootstat: Canonical boot reason: reboot` 를 곧바로 "SW 리부팅"으로 단정하지 않는다(전원 차단도 같은 값으로 기록된 사례). 종료 절차 로그 유무와 AMR 쪽 시각 복원 여부로 교차 판정한다.
- 전원이 끊기면 **AMR 로그 마지막 몇 초~수십 초가 유실**될 수 있다 → AMR 로그 최종 시각 ≠ 단전 시각. SoC 쪽 마지막 수신 시각과 부팅 기록으로 구간을 잡는다.

## 5. 통신 불량(E09) 판정 절차
- 의미: SoC 가 보낸 요청에 AMR 이 제때 응답하지 않음 (SoC 가 접속하지 못한 것과 다름). 직전 `AMRAgent: SocketTimeoutException` 이 흔하다.
- **발생/해제는 처리 로그로 판정**: `handleError From AMR: code = E09 ... status : 1`(발생) / `status : 2`(해제).
  클라우드 1분 주기 상태 보고에 들어 있는 에러 코드 건수는 **발생 횟수가 아니다**(유지 시간에 비례).
- **종료 3유형**: ① 정상 해제(status 2) ② 재부팅으로 소멸(해제 기록 없이 SoC 부팅) ③ 로그 끝까지 미해제. 해제 기록이 없다고 "계속 에러"로 단정하지 않는다.
- **원인 분류 순서** (현상 단계에서는 "어느 시그니처가 관찰됐는가"까지 기술):
  0. 업데이트(OTA) 진행 구간과 겹치는지 — 업데이트 중 앱 정지·로그 공백은 정상 절차
  1. 링크 끊김 반복(`Ethernet[eth0] is link-down/up`, 서비스 로그 `[NET] eth0 DOWN`)과 E09 시각이 전건 일치하는지 → 물리 선로 의심
  2. 링크·ping 정상인데 SocketTimeout 이 일정 간격으로 계속 → AMR 앱 무응답 (AMR 로그 공백과 대조)
  3. ping 까지 실패(`Ping to ...: Request timed out`), AMR 로그 급단절 → AMR OS 수준 정지 의심 (커널 로그 필요)
  4. E09 가 매번 SoC 재부팅 직후 발생 → 전원 순단의 결과일 수 있음 (부팅 기록 목록화부터)
  - 별도 유형: 링크는 up 인데 IP 통신이 안 되는 상태(ping 실패 + 게이트웨이 설정 실패 반복, link-down 0건)
- 접수 티켓 시각과 실제 발생 시각은 차이가 날 수 있다(대부분 수 초, 예외적으로 수 분). 고정값을 빼서 발생 시각을 정하지 않는다.
- "LAN LED 점등"이나 link-up 은 물리 계층만 보장한다. 셀프테스트에서 센서 데이터가 안 올라온 것을 센서 고장으로 단정하지 말고 AMR 쪽 센서 기동 로그를 먼저 본다.

## 6. AMR 앱 건강 상태
- `Required node [...] is NOT running` 이 지속되면 비정상(정상 시료는 0건). 이 상태가 길게 이어지다 앱 전체 무응답으로 진행할 수 있다.
- 노드 복구(재기동) 판정이 "노드가 보이는가"만 보면, 중복·좀비 노드가 남아 있어도 정상으로 오판한다 → **노드 존재 ≠ 기능 정상**.
- 같은 이름 노드가 2개 이상이면(중복) 토픽·서비스 충돌로 이후 기능이 계속 망가질 수 있다.
- 노드 configure/activate 소요 시간을 단계별로 표로 만들면 정상/지연이 바로 갈린다. 모든 단계가 고르게 느리면 시스템 전반의 지연(과열 스로틀링 등)을 의심한다.
- activate 가 센서(라이다) 켜짐을 기다려 오래 걸리는 것은 실패가 아닐 수 있다 — 센서 ON 시각과 완료 시각을 대조한다.
- 종료 처리 로그가 "이미 없는 프로세스" 직후에 "성공"으로 찍히는 등 **기록 자체가 틀리는 경우**가 있으니 앞뒤 줄을 함께 본다.

## 7. 상태 전이와 명령의 근거
- 상태 전이: `EXIT STATE: [A] -> Transition by SOC:[명령]|ROBOT:[이벤트] -> RUN STATE: [B]`. `SOC:[VOID]` 는 로봇 내부 이벤트에 의한 전이.
- **"외부(SoC)가 명령을 보냈다"의 근거는 수신 로그(`soc-cmd received : X`)와 그에 따른 발행 로그의 쌍**이다. 내부 토픽 수신 로그만으로는 보낸 주체를 알 수 없다.
- 첫 단계로 "수신 명령 종류별 건수"와 "상태 전이를 일으킨 명령 종류별 건수"를 비교하면 내부에서 만들어진 명령을 찾기 쉽다.

## 8. 위치 추정(로컬라이제이션) 실패
- TF 감시가 켜질 때 `map → odom` 변환이 빠지면 위치 추정 노드가 동작하지 않는 것이다.
- `pose(ts) stale by N s` 의 N 이 실제 시간과 같이 늘어나면 그 시점에 발행이 멈춘 것 → `로그 시각 − N` 으로 정지 시각을 역산한다.
- 라이다 주기(`checkScanHz`)가 정상이면 센서 문제가 아니다.

## 9. 업데이트(OTA) 로그
- 목표 버전과 설치 후 버전을 비교해 부분 실패(일부 모듈만 미갱신)를 찾는다.
- 업데이트 실패 후 강제 재부팅 → 재부팅 직후 통신 세션 미수립(E09)으로 이어지는 연쇄가 있을 수 있다.
- 서비스 로그의 네트워크 감시 줄은 계층별 상태(물리/ARP/IP/세션 수)를 보여준다. 세션 0 = 상대가 접속하지 않음.

## 10. 보고서(현상 정리) 작성
- 현상은 **시간순 ①②③**으로, 수치(시각·횟수·지속 시간·%)와 출처(파일:줄)를 붙여 쓴다. 정상으로 확인된 계층도 적는다.
- 타임라인은 AMR 시각 기준, `시각 | 출처(파일:줄) | 실제 로그 원문 | 설명` 으로 정리한다. 원문은 다시 검색할 수 있게 그대로 둔다.
- 원인은 "확인 범위 / 미확인"을 나누고, 후보는 우선순위와 근거를 단다. 로그로 판단할 수 없으면 필요한 추가 자료(현물, 커널 로그, 재채취 구간)를 적는다.
- 이상을 알게 되면 바로 로그를 채취하도록 요청한다 — 로그 회전으로 최초 발생 시점이 사라지기 쉽다.
